# 📘 Master Guide: Node.js Clustering & Scalability

## 1. The Core Problem: Why Clustering is Needed

**Concept:**
Node.js runs on the V8 engine, which is **single-threaded**. This means a single Node.js process has exactly one Event Loop and utilizes exactly **one CPU core**, regardless of how many cores your server actually has.

*   **The Constraint:** On an 8-core server, a standard Node.js app leaves 7 cores idle (0% usage).
*   **The Bottleneck:** If one request performs a heavy CPU task (blocking the loop), all other pending requests wait, leading to latency or timeouts.

**Solution:**
**Clustering** allows you to create multiple "child processes" (workers) that run simultaneously on the same machine, all sharing the same server port.

---

## 2. Architecture & Flowchart

**System Architecture:**
Each worker process is isolated. They do **not** share memory, but they share the network port managed by the Primary (Master) process.

```text
┌───────────────────────────┐
│         CLIENTS           │
└─────────────┬─────────────┘
              │ (Incoming Requests)
              ▼
┌───────────────────────────┐
│     PRIMARY (MASTER)      │ ◄── Spawns workers, owns Port 3000
│     (Cluster Manager)     │ ◄── Distributes connections
└──────┬──────┬──────┬──────┘
       │      │      │
       ▼      ▼      ▼
┌────────┐┌────────┐┌────────┐
│ Worker ││ Worker ││ Worker │ ◄── Each has its own V8 Instance
│   1    ││   2    ││   3    │ ◄── Each has its own Event Loop
└────────┘└────────┘└────────┘
```

## 3. Native Implementation (The "Hard" Way)

You can implement clustering using the built-in `cluster` module. This requires writing logic to distinguish between the Primary process (manager) and Worker processes (servers).

**Code Implementation:**

```javascript
const cluster = require('cluster');
const http = require('http');
const os = require('os');

// 1. Detect available CPU cores
const numCPUs = os.cpus().length;

if (cluster.isPrimary) {
  // --- PRIMARY PROCESS ---
  console.log(`Primary ${process.pid} is running`);

  // 2. Fork a worker for every CPU core
  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }

  // 3. High Availability: Restart worker if it crashes
  cluster.on('exit', (worker, code, signal) => {
    console.log(`Worker ${worker.process.pid} died. Restarting...`);
    cluster.fork(); 
  });

} else {
  // --- WORKER PROCESS ---
  // Workers share the TCP connection automatically
  http.createServer((req, res) => {
    res.writeHead(200);
    res.end(`Handled by Worker ${process.pid}`);
  }).listen(8000);
  
  console.log(`Worker ${process.pid} started`);
}
```
**

**Key Details:**
*   **`cluster.fork()`**: Uses an OS-level fork. Memory is copy-on-write, meaning workers handle their own memory allocation.
*   **Restart Strategy**: The `exit` event listener ensures that if a worker crashes, the master spawns a replacement instantly, keeping the app alive.

## 4. Load Balancing Strategies

How does the Primary process decide which worker gets a request?

1.  **Round-Robin (Default on Linux/macOS):**
    The Primary accepts the connection and distributes it to Worker 1, then Worker 2, etc. This ensures even load distribution.
2.  **OS Scheduling (Default on Windows):**
    Node.js allows the Operating System to decide which process handles the request. This can lead to uneven loads (e.g., Worker 1 doing 80% of the work).

**Configuration Tip:**
You can force Round-Robin on Windows using:
```javascript
cluster.schedulingPolicy = cluster.SCHED_RR;
```

## 5. The "Sticky Session" Problem (Critical Pitfall)

**The Problem:**
Because workers do not share memory, they do not share session data.
*   **Scenario:**
    1.  User logs in via **Worker 1**. Session is stored in Worker 1's RAM.
    2.  User sends a second request. Load balancer routes it to **Worker 2**.
    3.  **Worker 2** checks its RAM, finds no session, and logs the user out.

**Visual Failure Scenario:**
```text
Req 1 (Login)  ──> [Worker 1] (Session Saved in RAM)
      │
Req 2 (Profile) ──> [Worker 2] (RAM Empty) ──> ❌ ERROR: Not Authorized
```
**

**Solutions:**
1.  **Sticky Sessions (Not Recommended):** Configure the load balancer to hash the client IP so the same user always hits the same worker.
2.  **Centralized State (Recommended):** Use a database like **Redis** to store sessions. All workers connect to Redis. This makes the app **Stateless**.

## 6. PM2: Production-Grade Clustering (The "Easy" Way)

In production, manual `cluster` code is often replaced by **PM2**, a process manager that handles scaling, logs, and restarts automatically.

**Key Features:**
*   **Zero-Code implementation:** Write your app as a single file; PM2 handles the rest.
*   **Zero-Downtime Reload:** PM2 reloads workers one by one, ensuring no connections are dropped during updates.

**PM2 Commands:**

```bash
# Start app utilizing ALL available cores
pm2 start app.js -i max

# Scale to specific number of instances
pm2 scale app 4

# Zero-downtime reload (Rolling Restart)
pm2 reload app
```

## 8. Clustering vs. Worker Threads

It is crucial not to confuse these two concepts.

| Feature | **Clustering** (`cluster`) | **Worker Threads** (`worker_threads`) |
| :--- | :--- | :--- |
| **Unit** | **Process** (OS Level) | **Thread** (Inside Process) |
| **Memory** | **Isolated** (Separate RAM) | **Shared** (`SharedArrayBuffer`) |
| **Best For** | **Scaling Traffic** (e.g., 10k req/sec) | **CPU Heavy Tasks** (e.g., Image Resize) |
| **Cost** | Heavy (High RAM usage) | Lightweight |

**Rule of Thumb:**
*   If your API is slow because of **traffic volume** → Use **Clustering**.
*   If your API is slow because of **complex calculations** → Use **Worker Threads**.

## 9. System Limits (Stress Testing)

When scaling massively (e.g., 1 million requests), CPU is not the only limit:
1.  **Ephemeral Ports:** Every request uses a TCP port. A server has ~65k ports. You may run out of ports before CPU cycles (`EADDRINUSE`).
2.  **File Descriptors:** In Linux, network sockets are files. The default limit is often 1024. You must increase this limit using `ulimit -n 65000` to handle high concurrency.

### 2. Graceful Shutdown (Production Critical)
The sources emphasize that simply killing a process (like PM2 does during a reload) can drop active connections if not handled correctly.

**The Pattern:** You must listen for the `SIGTERM` signal to close the server **after** existing requests finish.

**Code Implementation:**
```javascript
const server = app.listen(3000);

process.on('SIGTERM', () => {
    console.log('SIGTERM received. Shutting down gracefully...');
    
    server.close(() => {
        console.log('Closed out remaining connections.');
        process.exit(0); // Exit success
    });
});
```

### 3. The "Blocking" Code Proof
The sources use a specific example to **prove** clustering works by blocking the event loop on purpose. This is often asked in interviews to demonstrate understanding.

**The Test:**
```javascript
// A heavy task that blocks the Event Loop for 5 seconds
app.get('/heavy', (req, res) => {
    const start = Date.now();
    while (Date.now() - start < 5000) {} // CPU Spin
    res.send('Done!');
});

app.get('/fast', (req, res) => {
    res.send('I am fast!');
});
```
*   **Without Cluster:** Hitting `/heavy` freezes the server. Hitting `/fast` immediately after **waits 5 seconds**.
*   **With Cluster:** Hitting `/heavy` blocks **Worker A**. Hitting `/fast` is handled immediately by **Worker B**.

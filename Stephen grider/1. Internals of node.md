Here are the structured notes and an explanation of the core concepts covered:

### 📝 Node.js Architecture Notes

**1. The High-Level Flow**

* **The Client:** A user (browser/mobile) sends a request to the Node.js server.
* **The Event Queue:** All incoming requests are first lined up in a queue (First In, First Out).
* **The Event Loop:** This is the "manager" that constantly watches the queue. It picks up requests one by one to process them.

**2. Handling Requests: The Fork in the Road**
When the Event Loop picks up a request, it decides how to handle it based on the type of operation:

* **Non-Blocking (Asynchronous) Operations:**
* *Examples:* Simple data processing, non-heavy tasks.
* *Action:* The Event Loop processes these **immediately** and sends the response back to the user.
* *Benefit:* Fast and keeps the loop free for other users.


* **Blocking (Synchronous) Operations:**
* *Examples:* Reading a large file synchronously (`fs.readFileSync`), heavy calculations.
* *Action:* The Event Loop cannot do this alone without stopping everything else. It delegates this work to the **Thread Pool**.



**3. The Thread Pool (The Workers)**

* **Role:** A group of "workers" (threads) that perform heavy, blocking tasks in the background.
* **Default Size:** By default, Libuv provides **4 threads**.
* **Workflow:** A thread picks up the task, completes it, and returns the result (callback) to the Event Loop, which then responds to the user.
* **Scaling:** You can increase the pool size, but it is limited by your machine's CPU cores (checked via `os.cpus().length`). If you have 8 cores, you can efficiently run 8 parallel threads.

**4. Code Example: Sync vs. Async**
The video demonstrates the difference using file system (`fs`) operations:

* **Blocking (`readFileSync`):** The program stops at line 2. It prints `1`, waits for the file, then prints `2`.
* **Non-Blocking (`readFile`):** The program initiates the read and moves on. It prints `1`, then `2`, and *later* prints the file content when it's ready.

## What actually implements the Event Loop?

👉 **libuv (written in C)**
Node.js **does not** implement the event loop in JavaScript.

**libuv** is responsible for:

* Event loop execution
* Async I/O abstraction
* Thread pool management

## High-Level Event Loop Structure (Internal)

This loop runs **continuously** on the **main thread**:

```
while (process is alive) {
  run timers phase
  run I/O callbacks
  poll for I/O
  run check phase
  run close callbacks
}
```

### Crucial Internal Detail

* If **nothing is pending**, Node **blocks in poll**
* If callbacks are ready, poll **returns immediately**

👉 This is why Node is:

* CPU-efficient
* Non-busy-waiting
* Scalable under I/O load

---

## Event Loop Phases (Mental Model)

```
┌ timers        → setTimeout / setInterval
├ I/O callbacks → completed fs / network
├ poll          → wait for I/O
├ check         → setImmediate
└ close         → cleanup handlers
```

# 007️⃣ Event Loop Ticks (00:39:11)

## What is a “Tick”?

> **One complete pass through all event loop phases**

```
1 tick = one full iteration of the loop
```

Ticks matter because **some queues bypass phases entirely**.

---

## Tick Priority Order (Very Important)

```
Current JS execution
→ process.nextTick queue
→ Promise microtasks
→ Event loop phases
```

### Why this matters

* `process.nextTick()` **does not wait**
* It executes **before the loop continues**

---

## Starvation Example (Video Highlight)

```js
function loop() {

}

```

### What happens?

* ❌ Event loop never reaches timers / I/O
* ❌ Poll phase never runs
* ❌ Application appears “hung”

👉 This is **event loop starvation**

# 011️⃣ Thread Pools with Multithreading (01:01:02)

## Key clarification (often misunderstood)

There is **ONE thread pool**, but it contains **multiple worker threads**.

```
┌─────────────┐
│ JS Thread   │  ← event loop (single)
└─────▲───────┘
      │ delegates async work
┌─────┴────────────────┐
│ libuv Thread Pool    │
│  T1   T2   T3   T4   │  ← default = 4 workers
└─────▲────────────────┘
      │
┌─────┴───────┐
│ OS / CPU    │
└─────────────┘
```

### Practical meaning

* CPU-heavy async tasks **do not block JavaScript**
* Excess tasks **queue up**
* Queueing = **latency**

---

## Observable experiment (thread pool saturation)

```js
const crypto = require("crypto");

for (let i = 0; i < 8; i++) {
  crypto.pbkdf2("a", "b", 100000, 64, "sha512", () => {
    console.log("done");
  });
}
```

### What you observe

* First **4** start immediately
* Remaining **4 wait**
* Confirms **finite worker pool**

# 016️⃣ OS Async — Common Questions (01:23:02)

### Why doesn’t Node use the thread pool for everything?

Because:

* OS async I/O is **faster**
* Thread pools consume **CPU + memory**
* Scaling networking via threads is inefficient

### Why does file system use the thread pool?

Because:

* Most OS file APIs are **blocking**
* libuv must offload them to workers

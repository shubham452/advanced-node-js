# Node.js Internals — Unified “Under the Hood” Notes

## 1️⃣ What Node.js Really Is (Architecture Mental Model)

**Node.js** is **not** just JavaScript.
It is a **runtime system** that allows JavaScript to interact with the operating system.

### Layered View

```
┌────────────────────┐
│ JavaScript Code    │  ← your app
└─────────▲──────────┘
          │
┌─────────┴──────────┐
│ V8 Engine          │  ← executes JS
└─────────▲──────────┘
          │
┌─────────┴──────────┐
│ Node.js APIs       │  ← fs, http, crypto, timers
└─────────▲──────────┘
          │
┌─────────┴──────────┐
│ libuv (C/C++)      │  ← event loop, async I/O, thread pool
└─────────▲──────────┘
          │
┌─────────┴──────────┐
│ OS Kernel          │  ← files, network, sockets
└────────────────────┘
```

### Key Insight

> **JavaScript never talks to the OS directly.**
> Everything goes through **C/C++ bindings** and **libuv**.

---

## 2️⃣ Threads vs Processes (Clearing the Biggest Myth)

### Definitions

* **Process**: Running instance of a program (memory + resources)
* **Thread**: Execution unit *inside* a process

### Node’s Reality

* ✅ **JavaScript runs on ONE main thread**
* ✅ **Node internally uses multiple threads**

### Where Threads Exist

| Component         | Thread Usage                   |
| ----------------- | ------------------------------ |
| JS Execution      | Single thread                  |
| Event Loop        | Single thread                  |
| libuv Thread Pool | Multiple threads (default = 4) |
| OS Network Stack  | OS-managed threads             |

👉 This is how Node stays **non-blocking**.

---

## 3️⃣ C++ Bindings & Why Async Works

JavaScript alone **cannot**:

* Read files
* Open sockets
* Perform async I/O efficiently
* Spawn threads

So Node provides **C++ bindings**.

### Example: `fs.readFile`

```js
console.log("start");

fs.readFile("file.txt", () => {
  console.log("file read");
});

console.log("end");
```

**Execution Flow**

```
JS → C++ binding → libuv → OS kernel
                          ↓
                   callback queued
                          ↓
                 event loop executes
```

**Output**

```
start
end
file read
```

👉 JS did not block — **C++ + OS handled the work**.

## 4️⃣ The Event Loop (Mental Model, Not Myth)

The video’s **pseudo-code model** is the correct way to think about the event loop.

### Pseudo-Code (Mental Model)

```js
while (shouldContinue()) {

  // 1. Execute expired timers (setTimeout, setInterval)

  // 2. Execute completed OS tasks & async operations

  // 3. Poll phase (wait if nothing else to do)

  // 4. Execute setImmediate callbacks

  // 5. Execute close handlers
}
```

### What `shouldContinue()` Checks

* Pending timers?
* Pending OS tasks? (network, servers)
* Pending async operations? (fs, crypto)

If **none exist**, Node **exits**.

---

## 5️⃣ Event Loop Phases (Simplified but Accurate)

```
┌ timers        → setTimeout, setInterval
├ I/O callbacks → network, fs
├ poll          → wait for I/O
├ check         → setImmediate
└ close         → cleanup handlers
```

### Microtasks vs Macrotasks

| Type       | Examples                           |
| ---------- | ---------------------------------- |
| Microtasks | `process.nextTick`, `Promise.then` |
| Macrotasks | `setTimeout`, `setImmediate`       |

### Priority Rule

```
process.nextTick
→ Promises
→ Event loop phases
```

Example:

```js
setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
process.nextTick(() => console.log("nextTick"));
Promise.resolve().then(() => console.log("promise"));
```

Possible output:

```
nextTick
promise
timeout / immediate
```

## 6️⃣ The libuv Thread Pool (Critical Concept)

Default size: **4 threads**

Used by:

* `fs`
* `crypto`
* `dns`
* `zlib`

### Proof via Crypto Example

```js
const crypto = require("crypto");
const start = Date.now();

function doHash(id) {
  crypto.pbkdf2("a", "b", 100000, 512, "sha512", () => {
    console.log(id, Date.now() - start);
  });
}

doHash(1);
doHash(2);
doHash(3);
doHash(4);
doHash(5);
```

### What Happens

* First **4** run in parallel
* 5th **waits**
* Total time increases

👉 **Thread pool saturation is real.**

You can change size:

```bash
UV_THREADPOOL_SIZE=2 node threads.js
```

## 7️⃣ Network I/O vs Thread Pool (Key Video Insight)

This is the **core distinction** the video reveals.

### Network / HTTPS

* Uses **OS async I/O**
* **Does NOT use libuv thread pool**
* Scales extremely well

### Crypto / FS

* Uses **libuv thread pool**
* Can be **exhausted**
* Can delay unrelated work

---

## 8️⃣ Answer to the Guiding Question

> **If a file download (network) and a password hash (crypto) start at the same time, which uses the thread pool?**

### Correct Answer

* ✅ **Crypto hashing uses the libuv thread pool**
* ❌ **Network download does NOT**

### Why

* Network I/O is handled by the **OS kernel**
* Crypto is **CPU-bound**, so Node offloads it to worker threads

### Real-World Consequence

> Heavy crypto or fs operations can starve your app
> **Network requests will still flow**

# 006️⃣ Event Loop Implementation (00:31:48)

## What actually implements the Event Loop?

👉 **libuv (written in C)**
Node.js **does not** implement the event loop in JavaScript.

**libuv** is responsible for:

* Event loop execution
* Async I/O abstraction
* Thread pool management

![Image](https://media.geeksforgeeks.org/wp-content/uploads/20200224050909/nodejs2.png)

## High-Level Event Loop Structure (Internal)

This loop runs **continuously** on the **main thread**:

```
while (process is alive) {
  run timers phase
  run I/O callbacks
  poll for I/O
  run check phase
  run close callbacks
}
```

### Crucial Internal Detail

* If **nothing is pending**, Node **blocks in poll**
* If callbacks are ready, poll **returns immediately**

👉 This is why Node is:

* CPU-efficient
* Non-busy-waiting
* Scalable under I/O load

---

## Event Loop Phases (Mental Model)

```
┌ timers        → setTimeout / setInterval
├ I/O callbacks → completed fs / network
├ poll          → wait for I/O
├ check         → setImmediate
└ close         → cleanup handlers
```

# 007️⃣ Event Loop Ticks (00:39:11)

## What is a “Tick”?

> **One complete pass through all event loop phases**

```
1 tick = one full iteration of the loop
```

Ticks matter because **some queues bypass phases entirely**.

---

## Tick Priority Order (Very Important)

```
Current JS execution
→ process.nextTick queue
→ Promise microtasks
→ Event loop phases
```

### Why this matters

* `process.nextTick()` **does not wait**
* It executes **before the loop continues**

---

## Starvation Example (Video Highlight)

```js
function loop() {
  process.nextTick(loop);
}
loop();
```

### What happens?

* ❌ Event loop never reaches timers / I/O
* ❌ Poll phase never runs
* ❌ Application appears “hung”

👉 This is **event loop starvation**

# 011️⃣ Thread Pools with Multithreading (01:01:02)

## Key clarification (often misunderstood)

There is **ONE thread pool**, but it contains **multiple worker threads**.

```
┌─────────────┐
│ JS Thread   │  ← event loop (single)
└─────▲───────┘
      │ delegates async work
┌─────┴────────────────┐
│ libuv Thread Pool    │
│  T1   T2   T3   T4   │  ← default = 4 workers
└─────▲────────────────┘
      │
┌─────┴───────┐
│ OS / CPU    │
└─────────────┘
```

### Practical meaning

* CPU-heavy async tasks **do not block JavaScript**
* Excess tasks **queue up**
* Queueing = **latency**

---

## Observable experiment (thread pool saturation)

```js
const crypto = require("crypto");

for (let i = 0; i < 8; i++) {
  crypto.pbkdf2("a", "b", 100000, 64, "sha512", () => {
    console.log("done");
  });
}
```

### What you observe

* First **4** start immediately
* Remaining **4 wait**
* Confirms **finite worker pool**

# 016️⃣ OS Async — Common Questions (01:23:02)

### Why doesn’t Node use the thread pool for everything?

Because:

* OS async I/O is **faster**
* Thread pools consume **CPU + memory**
* Scaling networking via threads is inefficient

### Why does file system use the thread pool?

Because:

* Most OS file APIs are **blocking**
* libuv must offload them to workers

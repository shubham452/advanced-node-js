## First: What are these “5 steps” really?

They are **phases of the event loop**.
Each phase answers **one specific question**:

> “Is there any work of *this type* ready to run right now?”

Think of the event loop as a **scheduler walking through queues**.

---

## The Big Picture (Mental Model)

```
One Event Loop Tick = check queues in THIS ORDER

1️⃣ Timers queue
2️⃣ I/O callbacks queue
3️⃣ Poll (wait / fetch new work)
4️⃣ Check queue (setImmediate)
5️⃣ Close callbacks
```

Each step = **a queue of callbacks**.

---

## 1️⃣ Execute expired timers

**(setTimeout / setInterval)**

### What this step checks

> “Are there any timers whose delay has finished?”

Example:

```js
setTimeout(() => {
  console.log("timer");
}, 1000);
```

After ~1000ms, this callback goes into the **Timers queue**.

### Important clarification

* `setTimeout(fn, 0)` does **NOT** mean “run immediately”
* It means “run in the **timers phase** of a future tick”

---

## 2️⃣ Execute OS & async callbacks

**(completed I/O like fs, network, DNS)**

### What this step checks

> “Did the OS or thread pool finish any async work?”

Example:

```js
fs.readFile("file.txt", () => {
  console.log("file done");
});
```

Flow:

```
JS → C++ → OS / thread pool → callback queued
```

When done, the callback waits in this **I/O callbacks phase**.

---

## 3️⃣ Poll phase (MOST IMPORTANT)

### What this step does

> “Do I need to WAIT, or do I already have work?”

Two possibilities:

### Case A: Nothing to do

Node **blocks here** and waits:

* new network request
* file finishes
* timer is about to expire

👉 This is why Node is **CPU efficient**

### Case B: Work exists

Node:

* pulls callbacks into queues
* **immediately continues**

---

## 4️⃣ Execute `setImmediate`

**(check phase)**

### What this step checks

> “Any `setImmediate` callbacks ready?”

Example:

```js
setImmediate(() => {
  console.log("immediate");
});
```

### Why `setImmediate` exists

It is designed to run:

* **after I/O**
* **before next timers phase**

This makes it predictable **inside I/O callbacks**.

---

## 5️⃣ Execute close handlers

**(cleanup phase)**

### What runs here

Cleanup callbacks like:

```js
stream.on("close", () => {
  console.log("closed");
});
```

Used for:

* releasing resources
* final cleanup

You rarely use this directly, but Node relies on it internally.

---

## Putting ALL 5 Together (One Tick)

```
┌─ 1. Timers (setTimeout)
├─ 2. I/O callbacks (fs, network)
├─ 3. Poll (wait or fetch work)
├─ 4. Check (setImmediate)
└─ 5. Close callbacks
```

Then:

```
tick ends → next tick begins
```

These are **NOT arbitrary steps**.
They explain:

* why `setTimeout(0)` is delayed
* why `setImmediate` behaves differently
* why Node doesn’t waste CPU
* why some callbacks feel “out of order”

## High-Level Event Loop Structure (Internal)

This loop runs **continuously** on the **main thread**:

```
while (process is alive) {
  run timers phase
  run I/O callbacks
  poll for I/O
  run check phase
  run close callbacks
}
```

### Crucial Internal Detail

* If **nothing is pending**, Node **blocks in poll**
* If callbacks are ready, poll **returns immediately**

👉 This is why Node is:

* CPU-efficient
* Non-busy-waiting
* Scalable under I/O load

# 011️⃣ Thread Pools with Multithreading (01:01:02)

## Key clarification (often misunderstood)

There is **ONE thread pool**, but it contains **multiple worker threads**.

```
┌─────────────┐
│ JS Thread   │  ← event loop (single)
└─────▲───────┘
      │ delegates async work
┌─────┴────────────────┐
│ libuv Thread Pool    │
│  T1   T2   T3   T4   │  ← default = 4 workers
└─────▲────────────────┘
      │
┌─────┴───────┐
│ OS / CPU    │
└─────────────┘
```

### Practical meaning

* CPU-heavy async tasks **do not block JavaScript**
* Excess tasks **queue up**
* Queueing = **latency**

---

### What you observe

* First **4** start immediately
* Remaining **4 wait**
* Confirms **finite worker pool**

# 016️⃣ OS Async — Common Questions (01:23:02)

### Why doesn’t Node use the thread pool for everything?

Because:

* OS async I/O is **faster**
* Thread pools consume **CPU + memory**
* Scaling networking via threads is inefficient

### Why does file system use the thread pool?

Because:

* Most OS file APIs are **blocking**
* libuv must offload them to workers

# 017️⃣ Review Section (01:25:42)

### Core truths (memorize verbatim)

* JavaScript runs on **one thread**
* Async ≠ multithreaded JavaScript
* Thread pool is **finite**
* OS handles networking directly
* Event loop schedules callbacks — it does not execute async work

# 019️⃣ Unexpected Event Loop Ordering (01:36:10)

## Inside an I/O callback

```js
const fs = require("fs");

fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
```

### Output

```
immediate
timeout
```

### Why this happens

* You are already **inside poll phase**
* `setImmediate` → **check phase (same tick)**
* `setTimeout` → **next timers phase**

# Final Mental Model (Lock This In)

* **Event loop** → scheduler
* **Thread pool** → limited workers
* **OS kernel** → async powerhouse
* **JS thread** → single decision maker

Node scales by **delegation**, not by parallel JavaScript execution.

# 020️⃣ Enhancing Performance (01:47:33)

## What “performance” means in Node.js

In Node.js, performance is **not about raw CPU speed**. It is about:

1. **Event loop responsiveness**
2. **Throughput (requests / second)**
3. **Latency under load**

If the event loop is healthy, Node feels “fast”.
If the event loop is blocked, Node feels “dead”.

---

## Core Performance Rules (Video Truths)

* Never block the **event loop**
* Delegate work to:

  * OS async APIs
  * libuv thread pool
  * multiple processes (clustering)

---

## Performance Hierarchy (Important)

```
Async I/O
   >
Thread Pool
   >
Worker Threads
   >
Clustering
```

👉 Node scales best by **doing less work per request on the JS thread**.

# 021️⃣ Why Express Is Discussed Here (01:49:51)

Express is introduced **not as a framework topic**, but as a **performance case study**.

```js
const express = require("express");
const app = express();

app.get("/", (req, res) => {
  res.send("Hello");
});

app.listen(3000);
```

### Critical Realization

* Express does **not** create threads
* Express does **not** parallelize requests
* Every request handler runs on the **same JS thread**

👉 **Express performance = event loop health**

# 022️⃣ Blocking the Event Loop (01:53:13)

## The Deadly Mistake

```js
app.get("/block", (req, res) => {
  for (let i = 0; i < 1e10; i++) {}
  res.send("done");
});
```

---

## What Actually Happens at Runtime

```
Request arrives
   ↓
Blocking JS loop
   ↓
Event loop frozen ❌
   ↓
All other users starve
```

### Why this is catastrophic

* JS thread is blocked
* Event loop cannot move
* No new requests are processed
* **One user freezes everyone**

This is why Node is called **single-threaded at the JS level**.

---

## Blocking Experiment (Expanded Version from Video)

```js
const express = require('express');
const app = express();

function doWork(duration) {
  const start = Date.now();
  while (Date.now() - start < duration) {}
}

app.get('/', (req, res) => {
  doWork(5000); // CPU spin
  res.send('Hi there');
});

app.listen(3000);
```

### Observed Behavior

1. User A hits `/` → waits 5 seconds
2. User B hits `/` 1 second later
3. User B waits **~9 seconds total**

👉 Because the **same JS thread** is reused.

# 023️⃣ The Core Limitation (02:00:20)

### Fundamental Truth

```
1 Node process
→ 1 Event Loop
→ 1 JS Thread
→ 1 CPU core
```

No matter how powerful your machine is, **a single Node process uses only one core**.

# 024️⃣ Clustering — The Idea (02:00:20)

### The Question the Video Asks

> “Why not run multiple Node processes?”

Each process:

* has its **own event loop**
* has its **own JS thread**
* runs on a **separate CPU core**

# 025️⃣ Forking Children (02:05:31)

## How Node Creates Multiple Processes

Using:

* `cluster`
* `child_process`

Forking means:

* new OS process
* separate memory
* separate event loop

---

## Master vs Worker Model

* **Master**

  * does not handle HTTP
  * manages workers
* **Workers**

  * run Express
  * handle requests

---

## Basic Forking Example

```js
const cluster = require("cluster");
const os = require("os");

if (cluster.isMaster) {
  const cpuCount = os.cpus().length;

  for (let i = 0; i < cpuCount; i++) {
    cluster.fork();
  }
} else {
  // worker process
}
```

# 026️⃣ Clustering in Action (02:11:09)

## Complete Clustered Server (Video Code)

```js
const cluster = require("cluster");
const express = require("express");
const os = require("os");

if (cluster.isMaster) {
  const cpuCount = os.cpus().length;

  for (let i = 0; i < cpuCount; i++) {
    cluster.fork();
  }
} else {
  const app = express();

  function doWork(duration) {
    const start = Date.now();
    while (Date.now() - start < duration) {}
  }

  app.get("/", (req, res) => {
    doWork(5000);
    res.send(`Handled by PID ${process.pid}`);
  });

  app.get("/fast", (req, res) => {
    res.send("This was fast!");
  });

  app.listen(3000);
}
```

---

## What Happens at Runtime

* OS distributes connections across workers
* Each worker has:

  * its own JS thread
  * its own event loop
* One blocked worker ≠ entire server down

---

## Cluster Manager vs Workers (Flow)

```
Client Requests
      ↓
Cluster Manager
      ↓
┌────────┬────────┬────────┐
│Worker1 │Worker2 │Worker3 │
│EventLP │EventLP │EventLP │
└────────┴────────┴────────┘
```

## Benchmarking Result (From Video)

### Without Clustering

* Request 1 → 5s
* Request 2 → 10s
* Request 3 → 15s

### With Clustering (4 workers)

* 4 simultaneous requests → **all ~5s**

Why?
👉 Separate processes, separate cores.

---

## Blocking vs Clustering (Key Comparison)

| Scenario          | Single Process   | Clustered         |
| ----------------- | ---------------- | ----------------- |
| CPU-heavy request | Blocks all users | Blocks one worker |
| Crash             | Server down      | Worker restarted  |
| CPU utilization   | 1 core           | All cores         |

# Critical Production Insight (Video Emphasis)

Clustering **does not fix bad code**.

If you:

* block the event loop
* use synchronous CPU-heavy logic

You will still hurt performance — just **one core at a time**.

```
Single Node Process

Clustered Node

 → N CPU Cores
```
